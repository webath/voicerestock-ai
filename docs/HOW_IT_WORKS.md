# Πώς δουλεύει το VORA (Voice Ordering & Restock Assistant) — βήμα βήμα

Από ένα τιμολόγιο στο ERP μέχρι ένα draft παραγγελίας που επιβεβαίωσε ο πωλητής στο τηλέφωνο.

```
 team_pack/ (CSV του ERP)
      │  ① ingestion & καθαρισμός
      ▼
 services/forecast ── ② πρόβλεψη εξάντλησης ──▶ submissions/team_*.csv (1.975 γραμμές)
      │                 ③ suggested orders + evidence
      ▼
 data/processed/*.json ──▶ ④ App API (FastAPI :8000) ──▶ ⑦ Mock ERP :8080  POST /api/draft-orders
                                 ▲          ▲
                    ⑤ Dashboard  │          │ ⑥ Voice agent (VPS, μέσω tunnel)
                    (Next.js :3000)         │    Pipecat + LiveKit SIP → κινητό πωλητή
                                            │
                              ⑧ Εξηγήσεις: Claude (claude-opus-5-5), μόνο από το evidence
```

---

## ① Ingestion & καθαρισμός — `services/forecast/src/forecast/ingest.py`

Το ERP (σχήμα SoftOne) έχει **headers** (`SALDOC`: ποιος, πότε, τι παραστατικό) και **γραμμές** (`MTRLINES`: είδος, ποσότητα).
Οι γραμμές *δεν* έχουν ημερομηνία ούτε πελάτη, οπότε:

1. **Join** `MTRLINES.FINDOC = SALDOC.FINDOC` → κάθε γραμμή παίρνει ημερομηνία, πελάτη, τύπο παραστατικού. 105.757 γραμμές, 0 ορφανές.
2. **Ακυρωμένα** (`ISCANCEL=1`, 362 παραστατικά) → έξω, *μαζί με τις γραμμές τους* (αλλιώς θα μετρούσαμε παραδόσεις που δεν έγιναν).
3. **Υπηρεσίες** (`MTRTYPE=1`, «Μεταφορικά») → έξω· δεν είναι εμπόρευμα.
4. **Πιστωτικά** (`SERIES=7071`, 457) → η ποσότητα γίνεται **αρνητική** (επιστροφή = λιγότερο απόθεμα στον πελάτη), ενώ στο ERP είναι θετική.
5. **Δώρα** (`PRICE=0`, ~6.500 γραμμές) → **μένουν**: παραδόθηκαν πραγματικά.
6. Άθροισμα ανά (πελάτης, είδος, μέρα) → 95.239 γραμμές «καθαρής ποσότητας».

Tests (`services/forecast/tests`) ελέγχουν κάθε κανόνα: 0 ακυρωμένες ποσότητες, πιστωτικά αρνητικά, 0 μεταφορικά, δώρα μέσα,
`NETAMNT` = Σ`LINEVAL`, καμία παράδοση Κυριακή.

## ② Πρόβλεψη εξάντλησης — `models.py` (μοντέλο `hybrid_v3`)

**Ερώτηση:** «Αν δεν πάει άλλη παράδοση, πότε θα τελειώσει το απόθεμα του πελάτη για αυτό το είδος;» για τα **1.975 ζεύγη**
πελάτη × είδους του `prediction_targets.csv` (ο κανόνας που τα διαλέγει αναπαράγεται ακριβώς: ≥3 αγορές και τελευταία ≤120 μέρες πριν,
+ τα ζεύγη των νέων πελατών).

Δύο εκτιμήσεις που ενώνονται:

**Α. «Ρυθμός & απόθεμα» (seasonal year-over-year)**
- Ρυθμός τελευταίων 90 ημερών (`r_recent`).
- **Μελλοντικός ρυθμός** = ρυθμός της *ίδιας περιόδου πέρσι* (Νοε–Ιαν) × φετινή τάση (φέτος/πέρσι, όριο 0,3–3).
  Έτσι πιάνει ότι τον χειμώνα πίνουν λιγότερα αναψυκτικά, ότι τα νησιά κλείνουν κ.λπ.
  Χωρίς περσινό ιστορικό → εποχικός δείκτης της ομάδας (κατηγορία είδους × περιοχή).
- **Απόθεμα σήμερα** ≈ τελευταία παραλαβή − ρυθμός × μέρες από τότε.
- **Εξάντληση** = σήμερα + απόθεμα / μελλοντικός ρυθμός.
- Αν ο μελλοντικός ρυθμός είναι ~0 (π.χ. ξενοδοχείο στις Κυκλάδες τον χειμώνα) → **κενό** = «καμία εξάντληση σε 90 μέρες» (189 ζεύγη).

**Β. «Κύκλος αγορών» (cadence)**
- Οι πελάτες παραγγέλνουν σε σταθερό ρυθμό (κάθε 7, 14… μέρες). Επόμενη εξάντληση ≈ τελευταία αγορά + διάμεσο διάστημα.
- **Προσφορές:** στο ιστορικό, στην προσφορά αγοράζουν ×1,48 και μετά ×0,42 → *κάνουν απόθεμα*, δεν καταναλώνουν περισσότερο.
  Αν η τελευταία αγορά ήταν σε προσφορά, η επόμενη έρχεται σε **~1,8× τον κανονικό κύκλο** (μετρημένο σε 1.576 περιπτώσεις,
  σχεδόν ανεξάρτητα από την ποσότητα). Αφορά 231 / 1.975 ζεύγη στο πραγματικό cutoff (Αναψυκτικά 5–18/10). Μελλοντικές προσφορές **δεν** αλλάζουν την εξάντληση.
- **Ληξιπρόθεσμα** (ο κύκλος έχει ήδη περάσει): η επόμενη αγορά όχι πριν από σήμερα + 3 μέρες (επόμενη επίσκεψη).
- **Νέοι πελάτες** με μία μόνο αγορά: κύκλος από **παρόμοιους πελάτες** (ίδιος τύπος, ίδιο είδος).

**Τελική ημερομηνία** = 0,9 × κύκλος + 0,1 × ρυθμός·απόθεμα **+ 3 μέρες** (το κενό έρχεται από το Α).
Τα +3: ο πελάτης ξαναπαραγγέλνει λίγο *πριν* μηδενίσει — η εξάντληση έρχεται λίγες μέρες μετά την επόμενη αγορά (βλ. παρακάτω).

**Πώς ξέρουμε ότι είναι καλό** (`backtest.py`, `docs/RESULTS.md`): «κόβουμε» το ιστορικό σε παλιές ημερομηνίες ίδιας εποχής
(31/10/2025, 29/11/2025, 4/10/2025), προβλέπουμε, και συγκρίνουμε με ό,τι έγινε μετά. Η «αληθινή» εξάντληση = επόμενη αγορά
+ 2 μέρες + 10% του κύκλου: με αυτό τα δύο σημεία αναφοράς της Revival (cutoff+30 ≈ 18,3, baseline ≈ 16,1) βγαίνουν κοντά,
ενώ με σκέτη την επόμενη αγορά όχι (~21 / ~15). Ίδιος υπολογισμός λάθους με τη Revival:

| | MAE (μέρες) | εντός ±3 | εντός ±7 |
|---|---|---|---|
| Revival baseline (μέσος ρυθμός 180 ημερών) | 13,2 | 26% | 54% |
| VORA v2 (`hybrid_v2`, submission 6/11) | 5,5 | 43% | 77% |
| **VORA v3 (`hybrid_v3`)** | **2,9** | **70%** | **92%** |

Σε όλες τις παραλλαγές truth που ταιριάζουν στα σημεία αναφοράς το v3 μένει 2,9–3,1.

Έξοδος: `submissions/team_*.csv` — 1.975 γραμμές, ημερομηνία ή κενό + `SUGGESTED_QTY`.

## ③ Suggested orders & evidence — `suggest.py`

Για κάθε πελάτη με είδη που τελειώνουν μέσα σε 3 εβδομάδες → **μία πρόταση** (124 συνολικά):

- **Ημερομηνία παράδοσης:** η τελευταία *μέρα δρομολογίου* του πελάτη (από τις μέρες που παίρνει συνήθως παραδόσεις) πριν την πρώτη εξάντληση,
  εργάσιμη, όχι αργία, όχι πριν τη Δευτέρα 2/11.
- **Είδη:** ό,τι τελειώνει ως μία εβδομάδα μετά την παράδοση (ένα δρομολόγιο, όχι πέντε).
- **Ποσότητα:** κατανάλωση ενός κύκλου αγορών με τον μελλοντικό ρυθμό +10%, μέσα σε 0,5×–2× της συνηθισμένης παραγγελίας.
  Στο backtest πέφτει ~1,1–1,5 μονάδες από την πραγματική επόμενη παραγγελία.
- **Όρια** `QTY_MIN..QTY_MAX` — ό,τι επιτρέπεται να αλλάξει ο πωλητής (dashboard ή φωνή).
- **Confidence:** όχι από AI — είναι το ποσοστό του backtest όπου η πρόβλεψη έπεσε μέσα σε ±3 μέρες, για πελάτες με
  παρόμοια σταθερότητα κύκλου.
- **Evidence:** ρυθμός (σήμερα / επόμενες εβδομάδες), τελευταία παραλαβή, κύκλος, εκτιμώμενο απόθεμα, εποχικός συντελεστής,
  προσφορά, νέος πελάτης, προειδοποιήσεις. **Ό,τι λέει ο AI βγαίνει από εδώ.**

Όλες οι 124 προτάσεις έχουν περάσει την επικύρωση του `POST /api/draft-orders` του ERP.

## ④ App API — `apps/api` (FastAPI, SQLite)

Το μόνο σημείο που διαβάζει/γράφει κατάσταση. Dashboard και voice agent μιλάνε **μόνο** με αυτό (`docs/CONTRACTS.md`).

Κύκλος ζωής μιας πρότασης:

```
proposed ──(αλλαγή ποσότητας)──▶ modified ──▶ confirmed ──(create-draft)──▶ posting ──▶ draft_created
                                                                              └──▶ failed (ξαναδοκιμάζεται)
```

Κανόνες που ισχύουν για όλους (dashboard και φωνή):
- **Αλλαγή ποσότητας** μόνο ακέραιος μέσα στα όρια, μόνο με τη σωστή `version` (αλλιώς 409: «άλλαξε από αλλού»).
- **Επιβεβαίωση** δίνει `confirmation_token` δεμένο στη συγκεκριμένη version. Μια νέα αλλαγή ποσότητας το ακυρώνει.
- **Draft** μόνο με έγκυρο token. Το POST στο ERP γίνεται μέσα σε lock· το ίδιο `idempotency_key` (ανά πρόταση) ή
  ήδη `draft_created` → επιστρέφει **το ίδιο** draft id. Ποτέ δύο drafts για την ίδια έγκριση.
- **Αξία (€)** = ποσότητα × τιμή καταλόγου 2026 — υπολογίζεται σε κάθε ανάγνωση, δεν πάει στο ERP.
- **Audit:** κάθε αλλαγή με ποιος (`X-Actor`: `dashboard`, `voice:<κλήση>`), τι, πότε.
- Νέο τρέξιμο του forecast → οι προτάσεις ξαναφορτώνονται· `POST /api/admin/reset` για «Επαναφορά demo».

## ⑥ Voice agent — `apps/voice` (Νίκος)

1. **«Κάλεσε»** στο dashboard → `POST /voice/calls {"salesman": 105}` → (tunnel) → agent στο VPS.
2. Έλεγχοι πριν καλέσει: ο αριθμός είναι στο allowlist, όχι ώρες ησυχίας, όχι ήδη σε κλήση, ο πωλητής έχει ανοιχτές προτάσεις.
3. **Κλήση:** LiveKit SIP → FreePBX → πάροχος → κινητό. Φωνή: `gpt-live-1` (ελληνικά)· τα εργαλεία τα χειρίζεται backend LLM.
4. Ο agent λέει ότι είναι **AI**, τι κινδυνεύει, και απαντά «γιατί;» **μόνο από το evidence**. Αριθμοί και ημερομηνίες λέγονται με λέξεις.
5. «Κάν' τα δεκαπέντε» → έλεγχος ορίων· αν είναι πάνω από 2× την πρόταση, **ξαναρωτά** («15 ή 50;»).
6. «Φτιάξ' το» → διαβάζει την **ακριβή περίληψη** (πελάτης, είδη, ποσότητες, παράδοση) και **περιμένει** «ναι».
   Αν αλλάξει κάτι στο μεταξύ (π.χ. από το dashboard), δεν γράφει.
7. «Ναι, επιβεβαιώνω» → confirm + create-draft στο App API με `idempotency_key = κλήση:πρόταση:version`.
   «Έγινε» λέει μόνο όταν επιστρέψει `erp_draft_id`.
8. Κάθε βήμα και κάθε φράση → `POST /api/calls/events` → η σελίδα Κλήσεις τα δείχνει ζωντανά.

Τηλεφωνητής / άλλος άνθρωπος / κλείσιμο γραμμής → καμία παραγγελία. Ο πωλητής βλέπει μόνο τους δικούς του πελάτες.

## Ένα παράδειγμα από την αρχή ως το τέλος — Mini Market Οικονομικό (1004)

1. Το Ice tea λεμόνι το αγοράζει κάθε ~14 μέρες· στις 10/10 πήρε **5** κιβώτια — σε **προσφορά Αναψυκτικών** (συνήθως 3–4).
2. Τον Νοέμβριο η κατανάλωση πέφτει (πέρσι ίδια περίοδο: ~μισή) → 0,09 κιβ./μέρα αντί για 0,19.
3. Ο κύκλος μεγαλώνει λόγω του αποθέματος της προσφοράς → **εξάντληση 6/11**.
4. Πρόταση: παράδοση **Πέμπτη 5/11** (μέρα δρομολογίου), 2 κιβώτια + 5 ακόμη είδη που τελειώνουν ως 12/11 — **325 €**.
5. Ο πωλητής βλέπει τον 1004 στο At Risk, ανοίγει τη σελίδα του, διαβάζει την εξήγηση και πατά «Κάλεσε» (ή «Έγκριση»).
6. Στο τηλέφωνο: «Γιατί δύο;» → εξήγηση από το evidence → «κάν' τα τρία» → περίληψη → «ναι».
7. Το API γράφει **ένα** draft στο ERP· η κάρτα της κλήσης και η παραγγελία δείχνουν `DRAFT-…`.
